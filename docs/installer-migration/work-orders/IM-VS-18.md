# IM-VS-18 — staged Microsoft layout trust boundary

Status: internal read-only contract decision analysis, 2026-10-01. No contract, manifest, source, VM, vendor file, or test changed. This is not blind technical, legal, or publication approval.

## Decision

**Yes, conditionally:** the underlying requirement can be met by a narrowly staged layout acquisition contract. Every byte of **code actually selected for execution** and every **input consumed before or during layout generation** must have a chosen expected pin, signature/version checks where required, and protected provenance *before* that vendor step. The generated layout, including every control and payload, must then match a separately reviewed complete inventory before any native **product installation**. A generated control cannot be compared before it exists. This permits no unexpected code, changed pin, missing source, mutable latest acquisition, or post-execution acceptance of a failed pre-execution check.

This would deliberately revise the stronger sentence at `contract-v1.md:297-300` requiring the whole resolved 409-file layout before **any** code from that layout runs. The requirement's general rule at `contract-v1.md:76-80` is per fetched artifact immediately before execution, and `:82-94` separately requires vendor install result/capability and final application validation. `:30-47` still forbids acquiring a `BLOCKED` parent or unpinned child. Thus the new phase boundary must be written explicitly in contract and executable tests; it cannot be inferred from the earlier successful install, or used while the canonical Microsoft route remains `BLOCKED`. Keep `:268-295` expected standalone Catalog, signed-channel contradiction and 140 size conflicts unchanged. The signed channel's external Catalog declaration is not silently made equal to the authenticated standalone Catalog.

## Minimum precise staged contract and tests

1. **Before layout acquisition/code:** first-party code downloads exact official fixed 17.14.41 bootstrapper, pinned OPC, signed standalone Catalog/Channel, and all 397 selected official payloads through protected recipient download. Verify exact URL/redirect policy, observed byte size, chosen SHA-256, required signer/chains, version/selection, and path/ACL/reparse safety. For the 140 size conflicts, retain signed declared sizes and independently observed delivered sizes; the 397 actual payload SHA values must still match the signed Catalog. Acquire no unreviewed `latest` engine. Preflight the complete 868-member OPC/installed-engine code closure and bootstrap immediately before execution; enumerate all executable child/module sources actually invoked or fail on an unknown source. Any locally authored `Layout.json`, `Response.json`, `--in` response, or other seed input gets its own reviewed content hash before the vendor reads it. A signed bootstrap alone is insufficient authority for unpinned downloaded code/data.
2. **Bounded layout generation:** in a disposable warm guest, use the verified installed engine and protected complete seed with the fixed bootstrapper. Test Microsoft's documented layout operation with the exact VC.Tools.x86.x64, Windows11SDK.26100 and en-US selection, `--quiet --wait --noUpdateInstaller`, plus local/offline controls. Disconnect the guest NIC during this experiment so a default/ignored update feed cannot introduce remote code; inspect bootstrapper/installer logs and process image/module paths. `--noWeb` can be included as a defense-in-depth diagnostic, but its documented guarantee does **not** cover engine update checks or conclusively cover layout acquisition. If the vendor requires another engine, tries a mutable source, changes code, ignores critical controls, or fails, preserve the failure; do not fall back to latest. No native product installer, MSVC package, or SDK package is permitted during this acquisition-only phase.
3. **Before product installation:** create a new explicit expected inventory for this exact locally authored/generated selection, with each generated control's reviewed pin and all 397 payloads plus OPC/bootstrap/metadata; retain the original 409-file inventory and differences as provenance. Do not change a failed old expected pin in place. Require exact count/path/size/hash, catalog-signature/selection and payload association checks, and Microsoft's `--verify` as an additional vendor check. Then invoke native interactive install using exact local catalog/channel/response, `--noWeb`, approved update source controls and native agreement UI; keep network isolation or an independently proven equivalent to prevent any mutable engine fetch. Check vendor exit, installed identity/capability, and final AutoClip source build and media flow separately.
4. **Focused failure tests before promotion:** wrong OPC/raw member/installed engine; untrusted signer; changed bootstrap; extra/missing executable path; changed generated control; unexpected default `useLatestInstaller`/remote URI; wrong catalog/channel identity; one changed or missing payload among 397; 140-size-conflict mishandling; interrupted/failed layout; `--noUpdateInstaller` ignored or non-zero; unknown module/network source; incomplete 41/409 source; TOCTOU mutation after hash. Each must stop before the next execution boundary. Preserve receipts/logs and previous installs.

## Next finite guest experiment and limit

Once the parent transports and hashes the full `51d099...` receipt, use the already installed, exact 868-match warm engine for **one layout-generation experiment only** after a first-party protected preload of the complete known official payload/input set and a hash-bound local control selection. Recheck installed engine and every acquisition input immediately before the vendor command; physically disconnect NIC; record exact command, return code, process/module/network observations, before/after engine closure, generated layout inventory and vendor logs. Do not reuse the incomplete 41-file source as a complete seed. A success would support the staged **warm-engine** path and inform an intentional contract/test revision. It would **not** qualify fresh engine acquisition on a clean recipient, original source disappearance, production online behavior, native interactive install, whole wizard, CPU build/media, or release.

Current contract left unchanged means **no vendor layout execution** under the new interpretation. A supported fresh-recipient engine acquisition route and its pre-execution checks remain required before changing Microsoft delivery classification. If the warm experiment cannot ensure that only the validated installed closure runs, stop with that precise blocker rather than relaxing to version-only or vendor `--verify` after execution.
