## Findings requiring correction or explicit contract resolution

1. **Cancellation is not checked at the next native-command boundary after the recipe.** `install.ps1:1216-1221` returns from the immutable recipe, then invokes `verify-install-wheels.py` at `:1225`, `uv pip install` at `:1228`, `uv pip check` at `:1233`, CPU import/capability at `:1235`, and possible GPU native commands at `:1242-1245`; the next cancellation check is `:1265`. A recipient may request cancellation during the recipe, yet these later native commands run after that recipe ends. This conflicts with `contract-v1.md:116-123` (cooperative cancellation at the **current native-command boundary**, no marker/launcher/activation after request). Smallest implementation correction: call the existing `Assert-AutoClipBuildCancellation` immediately after recipe completion and before each subsequent native command/side-effectful phase, with a final guard before launcher work. Keep the immutable recipe unchanged and retain the truthful “waiting for current build command” UI. Add one focused first-party fixture that requests cancellation while the recipe is pending and proves the first following native command is not invoked, plus the existing marker-race checks. This is a behavior correction under the repo's RED→GREEN rule, not a reason to weaken the contract to allow post-recipe commands.
2. **The cancellation signal has a startup window with no directory.** `AutoClip.iss:750-753` requires `<tmp>\source-build-N` not to exist; it enables “Cancel installation” and shows the page at `:781-788` before launching the helper. The helper creates that attempt directory only after its own input checks (`run-source-build.ps1:151-166`). `StopDownload` writes directly to `<attempt>\cancel.txt` (`AutoClip.iss:316-327`), so a click before creation can fail and display “Could not signal download cancellation.” The normal Cancel button is suppressed while `BuildActive` (`:330-335`), leaving the recipient to retry. Smallest correction: latch the request in Inno at click time and deliver the file as soon as the protected attempt directory appears; keep the page pending and fail closed if the supervisor exits before receipt of the signal. Do not precreate the directory behind a helper that requires a fresh absent attempt. Test that exact pre-directory click and terminal race in the Pascal decision fixture or an actual compiled-wizard fixture. This is a responsive-cancel reliability gap; it does not itself demonstrate marker activation.
3. **The final marker-to-launcher interval remains a race in the strict wording.** `install.ps1:1265-1273` catches cancellation before or immediately after marker creation and removes only its unchanged marker. `Install-AutoClipLaunchers` begins at `:1274-1278`, with no further check inside or immediately before that call. A signal arriving after the second check can be seen only by the outer worker when `install.ps1` returns, after launcher creation. The current focused fixture injects cancellation at the *second* check (`tests/InstallerBuildProcess.Tests.ps1:142-155`); it does not cover arrival after that check. Another check immediately before launcher creation and a deterministic test at that boundary are necessary, but do not make the literal guarantee atomic. If Cancel remains enabled through finalization, order cancellation and commit under a protected cutoff, or safely remove only the newly owned marker/launcher for a late accepted cancellation. Without one of those outcomes, the wizard can report cancellation while leaving a completion marker/launcher in the new layer. Resolve that precise boundary intentionally with `contract-v1.md:116-120`; do not claim the present code prevents **all** launcher work after **any** cancellation request.

## Supported conclusions and pending evidence

The typed handoff and source-build output redirection are a reasonable minimal integration of the existing wizard loop. The supervisor appears designed to wait for its actual worker and retain logs, and Inno's cancelled flag overrides a raced zero supervisor exit. The current contract already permits waiting through the immutable recipe; it does **not** permit running later native commands after the cancellation can first be observed. The startup signal window and marker-to-launcher race need the bounded corrections/tests above before a reliable cancel claim.

Required evidence remains: current exact ISCC compile and hashed receipt; a focused cancellation regression after the native recipe and before launcher; actual compiled wizard page/responsiveness and cancellation in a guest; source-build/health/media/lifecycle verification. The fake-ISCC input-lock suite and helper fixtures do not establish those outcomes. No uninstaller verification was performed or inferred.
