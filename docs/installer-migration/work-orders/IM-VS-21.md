# IM-VS-21 — bounded warm-engine layout acquisition handoff

Status: internal read-only preparation, 2026-10-01. This report did not change a contract, manifest, script, source artifact, VM, vendor installation, or classification. It is not independent technical or release approval.

## Decision and observed inputs

The next **bounded experiment** is a Microsoft bootstrapper `--layout` operation against a new protected guest layout directory while the guest NIC is physically disconnected. Use the already installed engine only if its complete 868-file OPC mapping still matches immediately before execution. This tests whether the pinned local content is enough for the vendor to generate a usable layout. It does not establish that Microsoft supports creating a layout without Internet: [Microsoft's layout guide](https://learn.microsoft.com/en-us/visualstudio/install/create-a-network-installation-of-visual-studio?view=visualstudio) expressly says Internet access and administrator permissions are needed for initial layout creation. A network request or offline failure is an experiment result, not a reason to fetch a mutable engine or change a failed pin.

## Minimum pre-execution handoff

1. In the **guest**, create a fresh absent, private, non-reparse layout directory, for example `<stage>\layout` (60-character absolute path, below Microsoft's 80-character layout-path limit). Do not repair or overwrite the historical incomplete source. Preserve the 397 preload files and receipt. Copy each payload from `<stage>\payloads\<relative path>` to the same **relative path at the new layout root**, using the reviewed path mapping; the payload directory itself is not a layout root. Verify exactly 397 expected payload paths, no extras, every actual length and Catalog SHA-256 under a read lock after the copy. The 140 signed-size differences remain explicit; the observed selected-byte pins are the expected incoming-file pins under the staged contract, not a rewrite of signed declarations.
2. Place only separately verified recipient-acquired controls in the new root: fixed `vs_BuildTools-17.14.41.exe` (4,473,792 bytes/SHA-256 `37bb0fb429d163ecebd272a865d11a37b906d152bef960da2ddb29c2e2fd6eeb`), `vs_setup.exe` (same bytes/hash), OPC, `vs_installer.version.json` (121 bytes/SHA-256 `e78a1053a6d59ad60ba8105623181b013c0ffc452216caada2699046f191974f`), selected Catalog/Channel, and the three pinned certificate files. Check their exact sizes/hashes, signatures/chains and fixed product/channel/version selection against the **reviewed selected identities**, including the already recorded Catalog/Channel signature evidence. These controls may be copied from the guest's surviving original source only after rechecking its complete relevant files and protected provenance; the host's historical completed layout is evidence, not a recipient download source. The original `Response.template.json` may be omitted as a vendor-generated output unless the actual bootstrapper requires it as an input; if included, treat its original 26,333 bytes/SHA-256 `6e016c4e259f739f2e65a68f2ffa80a1d85179d41e82e83e0bd9830eb1940639` as a pre-execution seed pin, then review any rewrite.
3. Author **new** `Layout.json` and, if the bootstrapper consumes it, `Response.json` with exactly `Microsoft.VisualStudio.Product.BuildTools`, `VisualStudio.17.Release`, the two selected components, `en-US`, local `installChannelUri`/`installCatalogUri`, and a local or deliberately non-existent `channelUri` update location. Avoid `useLatestInstaller: true` and any remote URI. Give each authored byte string an expected SHA-256 and validate it before vendor execution; preserve the original remote-URI JSON unchanged elsewhere for provenance. [Microsoft documents editing layout.json](https://learn.microsoft.com/en-us/visualstudio/install/create-a-network-installation-of-visual-studio?view=visualstudio) and says a layout response.json controls later client defaults. Do not assume these files override bootstrapper layout metadata selection until the operation and logs show that result.
4. Before launching the fixed bootstrapper, verify the protected root's ACL/reparse/path/duplicate and extra-file rules, all seed controls and payloads under read locks, bootstrapper signer and product identity, selected Catalog/Channel certificate chains, and current installed engine 868-member equality with the exact pinned OPC. The prior engine-mapping receipt is historical; repeat the complete check at point of use. Record an allowed vendor child/module source set and reject a newly selected unreviewed vendor executable/DLL/OPC. Preserve Windows trusted system-module provenance separately. Disconnect the guest NIC **after** inputs are complete and before vendor execution. Ensure an administrator context for `--quiet`, as Microsoft documents that standard users cannot invoke it programmatically.

The proposed **layout-only** invocation, after the above preflight and NIC disconnection, is:

```powershell
$layout = 'C:\Users\autocliplab\AppData\Local\Temp\vs p-c77a1261\layout'
& (Join-Path $layout 'vs_BuildTools-17.14.41.exe') --layout $layout --add Microsoft.VisualStudio.Component.VC.Tools.x86.x64 --add Microsoft.VisualStudio.Component.Windows11SDK.26100 --lang en-US --quiet --wait --noUpdateInstaller --noWeb
$LASTEXITCODE
```

This is a command proposal, **not an executed result**. [Microsoft's command-line reference](https://learn.microsoft.com/en-us/visualstudio/install/use-command-line-parameters-to-install-visual-studio?view=vs-2022) requires `--layout` as the initial layout parameter, permits repeated `--add` and `--lang`, and says `--wait` makes the bootstrapper return the operation result. `--quiet` supplies the documented condition under which `--noUpdateInstaller` prevents self-update and fails nonzero when an update is required. `--noWeb` prevents web retrieval of missing **product packages**; it does not suppress an update check and may not make layout creation offline-capable. Physical NIC isolation supplies that experiment boundary. `--installChannelUri`, `--installCatalogUri` and `--channelUri` are **install-command switches ignored by other commands**; therefore they are deliberately absent from this layout command. `--keepLayoutVersion` concerns product version when changing an existing layout and does not pin the engine, so it is also omitted. The fixed bootstrapper and observed local controls must select exactly 17.14.41, rather than infer exactness from the command alone.

Microsoft also documents that post-April-2023 bootstrappers use the latest installer by default. Omitting `--useLatestInstaller` is therefore insufficient on its own; the quiet/no-update condition, NIC isolation, pinned OPC/engine closure and observed logs are all necessary to detect and stop a different engine selection. This layout-only command does not constitute consent to product terms or permit a product-install transition.

## Output review and stop conditions

- Record the exact command line, privilege/NIC state, bootstrapper and installer return codes, complete vendor logs, process image and loaded vendor-module paths/hashes, remote-access attempts, seed inventory before/after, OPC and installed-engine closure before/after, and any generated `Layout.json`, `Response.json`, `Response.template.json` or other controls. A log saying the local OPC was signature-validated before engine extraction would support that *specific* vendor transition, not independent certificate verification already done by the mapping probe.
- On nonzero status, attempted download/update, unknown child/module, unexpected payload or code rewrite, missing package, or failed input check, preserve the original and experiment receipts and stop. Do not invoke `--fix`, reconnect to retry against `latest`, accept a replacement OPC, or run the product installer. The documented initial-layout Internet requirement makes an offline failure plausible.
- On zero status, review each generated/changed control and create a **new** expected full inventory from reviewed bytes and exact selection. Compare every root-relative payload and control, record intentional differences from the original 409-file inventory, verify Catalog/Channel signatures and selected associations again, and run vendor `--verify` as a supporting check only if the generated layout has the metadata it needs. A zero return or `--verify` cannot by itself authorize native product installation. The separately pinned complete layout must pass before a later native interactive product step, while the original 409 failure remains preserved.
