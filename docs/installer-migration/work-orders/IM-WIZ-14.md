## End-to-end code trace and disposition

- `AutoClip.iss:779-817` verifies the extracted bootstrap and exact helper identities, authors the typed argument JSON, and constructs one fixed native PowerShell command carrying the same five pins and fresh attempt path for both modes. `:818-831` resets state, builds `BuildRequestCommand`, sets `BuildActive=True` **before** showing the page, then launches the original supervisor. Thus a button click in the page-show/startup interval now routes through the requester rather than the download-only direct-file branch.
- Both the page's custom button and Inno's normal Cancel/Close event call `StopDownload` (`:320-372`). During a build, it starts the **same pinned helper** asynchronously with only `-RequestCancellation` appended; the UI says the decision is pending, disables the custom button and does **not** yet set `DownloadCancelled` (`:323-336`). Ordinary download cancellation remains a separate direct signal (`:338-344`). There is no build-mode direct write to `cancel.txt` in this adapter.
- The helper reopens/hash-checks its bootstrap, manifest, downloader, authored arguments and own script (`run-source-build.ps1:126-136`). Request mode waits up to ten seconds for the supervisor-created protected directory/decision lock and ten seconds on lock contention (`:137-151`, `:74-84`), then under the exclusive lock validates a bound `commit.json`. It writes `cancel.txt` and returns **0 only if no commit exists**; a valid commit returns **170 without a signal**. Unsafe/malformed or timed-out state returns another nonzero. Supervisor creates that lock before worker launch (`:173-191`); worker and supervisor check commit/cancel before terminal status (`:153-171`, `:192-197`). The bootstrap's matching lock and `COMMIT_STARTED` write precede marker/launcher action (`install.ps1:138-169,1309-1317`). This supports the contract's request-versus-acceptance ordering, while the immutable recipe can still run to its whole invocation boundary (`contract-v1.md:122-135`).
- Inno polls the requester while animating and observing the **original** supervisor (`AutoClip.iss:835-843`). `PollBuildCancellation` accepts only requester exit **0**, then sets `DownloadCancelled`; **170** closes further request attempts and displays “too late”; other codes display failure and permit a retry (`:347-365`). The main loop waits until both supervisor and pending requester have ended, and success requires the supervisor's exit zero **and** no accepted-cancellation flag (`:835-843`). `finally` waits for any pending requester even if the original supervisor failed to start, then for a started supervisor, before hiding the page (`:844-857`). The helper itself waits for the worker's terminal state. No request timeout is treated as accepted cancellation, and no worker/vendor process is killed.
- The inspected first-party helper test executes real requester-before-startup, accepted-before-commit, late-during-commit, invalid-commit and live-worker cases (`tests/InstallerBuildProcess.Tests.ps1:60-99,145-211`). It does **not** execute this Inno event handler or prove visible wizard responsiveness. The repository's guarded-builder tests use a fake compiler. An exact ISCC syntax compile is useful, but is not a running-page or cancellation acceptance test. The parent reports an earlier automatic policy rejection of compiled `/AUDIT` execution; this review neither retries nor bypasses it.

## Remaining findings and minimum follow-up

1. **Late request UI if normal Cancel/Close remains available:** exit 170 sets `BuildCancellationClosed=True` and leaves the custom button disabled (`AutoClip.iss:358-360`). If Inno delivers another normal Cancel/Close event, `CancelButtonClick` sets `Cancel=False` and calls `StopDownload` (`:367-372`), which silently returns on the closed latch (`:324`). The code path makes a repeated click ineffective; whether that native control is visibly enabled on the progress page is unverified without executing the compiled wizard. This does not corrupt the serialized decision, but could weaken the required “too late” disclosure. Minimum UI fix if the control remains available: disable it at 170 or show the stable too-late status when it is clicked, keeping the progress page visible until the same supervisor exits. Test the late-170 event path in an actual compiled Pascal fixture.
2. **Committed failure can strand a misleading source marker.** This is adjacent to, not a flaw in, request serialization. `install.ps1:1309-1317` writes `.install-complete` before creating the install-folder launcher and catches launcher failure as a warning. `AutoClip.iss:921-926` later requires `AutoClip.lnk` and returns an error when absent; `install.ps1:875-876` then refuses a same-root retry because the marker exists. Conversely, if a launcher is written but marker creation or a later action fails, the incomplete-root scan rejects the unexpected launcher at `install.ps1:1153-1163`. A `COMMIT_STARTED` record means cancellation is too late, **not** that finalization succeeded, as IM-WIZ-13 notes. Minimum separate lifecycle correction: make the wizard route's required launcher and completion-marker ordering/failure handling coherent, and test both failure orders without overwriting the previous release. Do not infer wizard success from commit existence, supervisor zero, or the source marker alone.
3. **Inno wiring still lacks executed decision evidence.** The helper's host race suite proves the request/commit primitive; static inspection proves the Pascal code intends to use it. Neither proves that the compiled page dispatches both buttons, stays responsive, correctly displays pending/0/170/other outcomes, and waits after a launch failure. The narrow first-party route, if compiled diagnostic execution is allowed, is to reuse the existing `InstallerMsys2Wizard.Tests.ps1` pattern: compile the *actual unchanged* `StopDownload`, `PollBuildCancellation`, `CancelButtonClick` and `RunSourceBuild` Pascal bodies into a diagnostic setup, substitute only the native helper/acquisition boundary with first-party requester/supervisor fixtures, and assert observed page decisions and terminal waits for startup 0, late 170, other-nonzero, and supervisor launch failure. Keep fixture outputs/path pins and exact compiler hash; do not equate matching source strings with executed callbacks. If executable policy still rejects the diagnostic, retain syntax compile plus helper evidence as partial and leave the exact UI qualification gate open. Later guest execution of the actual hashed Setup remains necessary for the normal wizard, CPU build, health/media and lifecycle claims.

No additional adapter change is required to assert the **narrow code-level protocol** in the inspected snapshot: acceptance only on 0; 170 never writes cancellation; failures are disclosed without changing the worker result; original supervisor/requester are both observed. The two concrete follow-ups above concern recipient-visible late Cancel behavior and finalization failure state. The compiled Inno and guest behavior are unverified here.
