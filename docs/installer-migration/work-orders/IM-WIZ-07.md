## Current behavior and why a PowerShell window appears

`installer/AutoClip.iss:695-785` performs Python, MSYS2, pinned downloads and then the **whole** `install.ps1` in `PrepareToInstall`. The download page is hidden at `:738`. At `:774-775`, `ExecWithNativeSysDir(..., SW_SHOW, ewWaitUntilTerminated, Code)` runs PowerShell synchronously without a wizard build page or output callback. A console can therefore be visible while the wizard waits on the Preparing to Install stage. The exit-zero follow-up checks only the helper marker, release manifest hash and launcher (`:779-784`), which does not establish whole wizard/health/media success. The contract requires phase progress, cancellation without harming the previous install, and validation before activation (`contract-v1.md:65-99`; `docs/runtime-update-architecture.md:25`).

The exact v40 ZIP inspected read-only is SHA-256 `f2b3be779294bc55d6f5f56c2a780a2d6b863486f3af9bd7d19f30051961fc9f`; its immutable `build-native-from-source.ps1` is SHA-256 `f384d9f55c78b5dd47cb7432fa7a0003e7ae6e07984f06a7231d42fdeed8e832`. Recipe `Invoke-Checked` pipes tool output to `Out-Host` (`:16-20`), and Git, tar, uv, MSYS bash, CMake/MSBuild and wheel verification can emit a large volume. It uses `Write-Host` only for cache reuse and final success (`:148`, `:221`); there is no stable machine-readable phase/progress protocol. `install.ps1` writes some high-level `Write-Host` messages, calls the recipe synchronously at `:1200-1207`, and writes `.install-complete` at `:1251`. The immutable recipe has no cancellation input. A numeric percent for compilation cannot be honestly inferred from this output; a marquee with named phases and recent lines is the truthful UI.

The existing wizard already has the right **responsive-loop pattern**: `DownloadArtifact` (`AutoClip.iss:319-361`) and `RunMsysProcess` (`:397-417`) launch `WScript.Shell.Exec`, poll `Process.Status`, call `DownloadPage.Animate; Sleep(100)`, and use `StopDownload` (`:308-317`) to write a cancellation file. The page/stop button are created at `:647-654`. The code currently calls `ReadAll` on stdout/stderr only **after** process exit. That is tolerable only for small bounded helper output; a full build's pipes can fill and stall the child before exit. Reuse the loop/page/button, but route large build output to a protected incremental log and display a bounded tail while polling. The original full log should remain available on failure/cancel.

## Minimum implementation handoff

1. Keep `PrepareToInstall` and the existing `DownloadPage`. After verified inputs and before `install.ps1`, show it with a source-build caption and change the Stop button text to “Cancel build.” Use an asynchronous `WScript.Shell.Exec` + `Process.Status` loop as in `DownloadArtifact`, launching the native System32 PowerShell with `-WindowStyle Hidden`; call `Animate`, update coarse **first-party** phase text, and show only a bounded recent-line memo from output. Hide in `finally`. Preserve the existing fixed argument list, exact helper/manifest hashes, launch result, exit code, cancellation flag and install path. Do not move work to `[Run]` merely for its `logoutput` flag: that changes installation ordering/commit behavior.
2. Have a tiny **pinned first-party PowerShell boundary** put all build stdout/stderr/information into a protected per-attempt log, with stable phase records and its own nonzero cancellation status. Windows PowerShell 5.1 [all-stream redirection](https://learn.microsoft.com/en-gb/powershell/module/microsoft.powershell.core/about/about_redirection?view=powershell-5.1) can capture `Write-Host` and other redirectable streams; its Progress stream is not redirectable, so the UI must rely on explicit phases plus source/native text. Keep WSH stdout/stderr tiny and drain them while polling or route them to files too; otherwise the current post-exit `ReadAll` pattern can deadlock on a verbose build. Use protected, task-owned log/cancel paths; verify no reparse/foreign-write ancestor and bind the attempt to the exact new install/build roots. The wrapper must propagate a reliable exit code and keep untrusted native text out of phase/control parsing. This adds no plugin or change to the immutable v40 recipe.
3. A click on the custom Stop button writes a protected cancel signal, disables further clicks, marks the run cancelled, and leaves the page visible with “Stopping after the current build command.” The first-party wrapper checks it before invoking each phase and after the synchronous immutable recipe returns; **`install.ps1` itself needs a small `-CancelPath` check immediately before its `.install-complete` write at `:1251` and launcher/activation work**. A wrapper alone cannot intercept that inner boundary. This is the **minimum safe cooperative semantics**: it may wait a long time inside Git/FFmpeg/MSBuild because the recipe cannot poll the file. On cancellation, return nonzero, never promote the new layer, leave the old active layer and user data untouched, and retain the incomplete owned staging/log for verified retry or bounded later cleanup. A cancelled flag overrides even a raced zero helper exit/marker when deciding wizard success.
4. If product requirements demand **prompt** cancellation during a native command, add only a scoped process-tree supervisor for the fresh **source-build phase**, after vendor prerequisites finish. Microsoft's [`taskkill /pid <pid> /t /f`](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill) targets a PID and its descendants; Windows [ordinary process termination does not kill children](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process). `WshScriptExec.ProcessID` is documented in Microsoft's original Windows Script Host 5.6 reference ([archival copy, page 180](https://isvbscriptdead.com/resources/windows-script-host.pdf)); the current Inno code does not use it. A bare PID is not authority: verify current process identity/owner/session/creation time and the source-only phase before acting, hold/confirm the root is still alive, never kill by image name, never target shared vendor installers, wait for every owned child to exit, and fail closed if identity or containment cannot be proven. If those checks cannot close the PID reuse/detached-child race, use an owned Windows Job Object in the narrow first-party supervisor rather than `taskkill`; do not claim prompt safe Cancel from `Terminate` of only the PowerShell parent. This stronger path needs its own tests and guest proof. It is not supplied by Inno's `ExecAndLogOutput`.
5. Tests for implementation: a synthetic chatty child (> pipe capacity) proves no hang and live bounded output; one emitted phase reaches page text; Stop during a long owned child proves no orphan, marker, activation or old-layer mutation; stop immediately before marker checks the race; invalid/unwritable cancel/log path stops before build; canceled child and wrong/nonzero exit preserve logs and old state; vendor installer phase never becomes a kill target. Then exact compiled wizard guest pass must demonstrate normal UI, media/health and lifecycle checks separately. None was executed here.
