Read-only, same-session internal engineering review of `installer/AutoClip.iss` and `installer/write-setup-receipt.ps1`. This is not independent, external, release, or legal approval. Source was inspected on 2026-10-02; no compiled Setup, vendor installer, VM, or uninstaller was run for this review.

## Registration binding: corrected

- Inno Setup 7.1 writes `InstallLocation` with a trailing backslash (`AddBackslash(WizardDirValue)`) and creates the uninstall key from the expanded AppId plus `_is1`: [Setup.Install.pas](https://github.com/jrsoftware/issrc/blob/is-7_1_0/Projects/Src/Setup.Install.pas#L273-L280), [Setup.MainFunc.pas](https://github.com/jrsoftware/issrc/blob/is-7_1_0/Projects/Src/Setup.MainFunc.pas#L336-L369). The previous helper compared that native value to a path without the trailing slash and would reject a normal installation.
- The current helper, SHA-256 `ba215751b9708e1507dbef591b11910b5766877286ce5a144f016a5eafcf889d`, compares the native value to `($SetupRoot+'\')` at lines 238 and 287, preserves the registry spelling in the receipt, and still binds the quoted `uninsNNN.exe` to that root. The parent reports a native-format fixture RED (`Native registration snapshot binding differs`), then GREEN library and CLI suites after this fix. I inspected the corrected source and hash; I did not rerun those tests.
- The per-user `HKCU` Registry64 lookup and quoted uninstaller path are consistent with the current `[Setup]` settings and Inno's native registration. Inno commits the uninstall registry entry and saves the uninstall log before `ssPostInstall`: [Setup.Install.pas](https://github.com/jrsoftware/issrc/blob/is-7_1_0/Projects/Src/Setup.Install.pas#L2865-L2879), [Setup.UninstallLog.pas](https://github.com/jrsoftware/issrc/blob/is-7_1_0/Projects/Src/Setup.UninstallLog.pas#L1289-L1316). The receipt can bind the generated EXE/DAT and registration at this step; no `ssDone` move is indicated by this ordering.

## Remaining findings

1. **Failure text can be overwritten on the Finish page.** `AutoClip.iss:1024-1034` sets `FinishedLabel.Caption` during `ssPostInstall` after a finalization failure. Inno subsequently calls `ChangeFinishedLabel` while preparing the Finish page, assigning the standard completion body: [Setup.MainForm.pas](https://github.com/jrsoftware/issrc/blob/is-7_1_0/Projects/Src/Setup.MainForm.pas#L220-L272), [Setup.WizardForm.pas](https://github.com/jrsoftware/issrc/blob/is-7_1_0/Projects/Src/Setup.WizardForm.pas#L1394-L1404). This is a source-order contradiction; a compiled UI fixture is still needed to establish the visible result. Smallest fix after meaningful RED: retain the failure flag at `ssPostInstall` and assign the failure heading/body in `CurPageChanged(wpFinished)` after Inno's assignment. Keep the nonzero exit behavior.
2. **An exceptional display call can leave the child unobserved.** `AutoClip.iss:999-1002` starts the WSH finalizer and calls `DownloadPage.SetText` and `Show` before entering the `try/finally` at line 1002. If either call raises, the outer `CurStepChanged` handler records incomplete status while the child may still finish and publish the receipt. No such failure has been observed. The smallest containment is to enter `try/finally` immediately after `Shell.Exec` and observe the exact process to terminal even when page display fails. A narrow injected-failure or fault fixture should prove this path without running a vendor installer.

The current `GetCustomSetupExitCode` returns 20 when `SetupReceiptComplete` remains false (`AutoClip.iss:1038-1041`). Inno calls this override at deinitialization following an otherwise successful install: [Setup.Start.pas](https://github.com/jrsoftware/issrc/blob/is-7_1_0/Projects/Src/Setup.Start.pas#L249), [Setup.MainFunc.pas](https://github.com/jrsoftware/issrc/blob/is-7_1_0/Projects/Src/Setup.MainFunc.pas#L3966-L3976). The native uninstall registration has already been committed; the UI must describe this incomplete receipt state accurately.

## Corrected withdrawal and scope

I withdraw the earlier claim that successful finalizer output could fill WSH stdout with the full file inventory. `Write-SetupReceiptRecord` returns only `{path,bytes,sha256,status}` (`write-setup-receipt.ps1:150-165`); `Write-SetupInstallationReceipt` returns that descriptor at line 244; the CLI writes a descriptor file and emits only that bounded descriptor at lines 300-304. The inventory remains in the receipt file. There is no observed success-stream deadlock in this path.

The request generated at `AutoClip.iss:979-990` supplies the expected context, pinned source handoff, setup identity, source supervisor pin, four native notice rows, and shortcut identity; the finalizer bounds and pins that request at `write-setup-receipt.ps1:255-269` and derives the native uninstaller identity from the registry at lines 280-300. I found no further concrete field mismatch in that inspected boundary. Compilation is parent-reported syntax evidence only; native Finish-page behavior, exceptional process observation, and full receipt publication remain unqualified by this review.
