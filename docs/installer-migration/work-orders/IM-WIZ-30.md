The user-directed order and the explicit warning that Inno's shell log does not cover helper-created files are in `plan.md:3-12`. The runtime architecture independently retains current/previous app and required runtime layers, active state, rollback targets and user database (`docs/runtime-update-architecture.md:84-98`).

## Smallest later implementation

1. After the exact wizard passes its final installed-health gate, create one versioned, protected setup-owned receipt for this installation. Bind fixed AppId, exact setup SHA-256, release ID/root, archive and manifest hashes, dependency manifest hash, and each **actually created and verified** runtime/setup leaf by relative path, bytes and SHA-256. Record shortcut target/arguments and the installed registration identity. Capture a fresh-owned root or authenticate matching partial-state provenance before claiming files already present. Do not infer ownership from a recursive snapshot of a foreign/preexisting directory. Preserve the receipt outside the runtime subtree it controls, with an exact schema and protected atomic write. Inno's source-build marker and native receipt remain inputs; they are not the final setup ownership receipt (`contract-v1.md:89-100,183-189`).
2. Add the smallest native Inno uninstall hook to read and validate that receipt and current paths, then delete only matching regular files with no reparse escape. Remove enumerated empty directories from the bottom up; retain a directory containing any unknown/changed file. Let Inno's native uninstall log manage its own registered shell files, icon and registration only after testing that it preserves modified artifacts as the contract requires. If its behavior cannot provide that guarantee, use an explicit matching-byte conditional removal for affected shell files. Do not use `[UninstallDelete]` wildcards or `filesandordirs`: the [Inno documentation](https://jrsoftware.org/ishelp/topic_uninstalldeletesection.htm) explicitly warns against broad deletion, and recursive deletion conflicts with the contract. `CurUninstallStepChanged` is a [supported native uninstall event](https://jrsoftware.org/ishelp/topic_scriptevents.htm); use one bounded event/helper, not a new general cleanup framework. Preserve a readable result listing removed, changed, unknown and locked files.
3. Before deleting a runtime leaf, compare its identity with current/previous activation and any other setup receipt. An exact current or rollback reference blocks removal until a compatible selection is explicitly and safely updated. Do not remove Microsoft/Python/Git/uv/VC installs, recipient publisher caches, Python setup logs, prior releases, private MSYS roots or source logs merely because they sit near AutoClip. A later explicit cleanup policy for private build roots needs a complete post-transaction inventory and reference decision; current base/package receipts are insufficient for whole-tree deletion.
4. At the later lifecycle gate, test the **exact generated uninstaller** on the qualified installed candidate. Freeze a before inventory and registration/shortcut state, add an unknown file and a modified owned file in the release, retain projects/settings/layouts/media/exports/ZIPs/credentials/caches and an older rollback layer, then run uninstall and compare every leaf/registration after. Require all unchanged owned leaves and owned links removed, unknown/changed and protected user/shared state retained, and explicit reporting of locked leftovers. Test a second invocation and a reused/repaired same-AppId setup only if those installation paths are actually supported. Record exact setup/uninstaller hashes and primary logs. This testing is deferred by the user order, not waived.
