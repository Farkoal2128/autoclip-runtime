# IM-MS-07: contract proposal for an exact MSYS2 base TAR route

Status: read-only engineering proposal. The official same-release TAR has passed a bounded guest **base-initialization** experiment; a production TAR route, five-package transaction, guarded source build, complete wizard, vendor-rights decision, and publication have not passed. This work order changes no manifest, helper, contract, VM, or delivery classification. It is internal analysis, not independent or external approval.

## Observed boundary

The [official MSYS2 installer guide](https://www.msys2.org/docs/installer/) lists `.tar.xz` as a base distribution and says an extracted archive followed by one login shell yields a functionally equivalent installation. The [official reinstallation guide](https://www.msys2.org/wiki/MSYS2-reinstallation/) says to untar the base, run `msys2_shell.cmd`, then exit. This supports an installer-owned private root without the GUI's shortcuts or maintenance tool; it does not specify AutoClip's trust, cleanup, or protected-root controls.

[IM-MS-02](IM-MS-02.md) records the official `2026-06-11` release TAR `msys2-base-x86_64-20260611.tar.xz`, **53,555,380 bytes**, SHA-256 `a2d047e8ee213c3c6a49a8de427eb1069df12207c0422ff1b3cbb5c905c34221`, and the separately pinned detached signature, checksum file, official package list, and installer signing-key fingerprint. Developer-side `gpgv` verification used the fingerprint published by the official guide, `0EBF782C5D53F7E5FB02A66746BD761F7A49B0EC`. This installer key is distinct from the TAR-delivered package-signing keyring. The exact release asset URL is `https://github.com/msys2/msys2-installer/releases/download/2026-06-11/msys2-base-x86_64-20260611.tar.xz`.

Parent's primary guest receipt `D:\AutoClip-Inno-Migration\vm-msys-tar-20261001.json`, SHA-256 `e5d7178803644ac4558280b0c540ca28142328f8398e8ba77ddedce1f6d2eaa8`, reports base phase `complete`, 15,529 regular files and 1,052 directories verified, valid TAR signature against the separately obtained pinned installer key, successful local default key initialization/population, one offline login, post-install effects, and 90 base package versions matching the official list. Its `base.tar_sha256=7aa6a7b0ecb72133c9a091d5006425bc9de51bece6863f014e1f63e43133e240` identifies the **native Windows tar tool**, not the TAR archive. The receipt's top-level `package_status=failed`: the staged package helper could not launch under the guest PowerShell execution policy. Later package attempts and [IM-MS-06](IM-MS-06.md) are separate evidence; this receipt does not qualify the five-package step. It is a diagnostic guest result, not a recipient wizard or lifecycle result.

The current [dependency manifest](../../../release/manifests/installer-dependencies-v1.json) `MSYS2` row (lines 214-425) still pins the **94,016,640-byte GUI EXE**, QIFW `in` arguments, 12 installed-file samples, five exact package/signature pairs, and `BLOCKED`. [The package helper](../../../installer/install-msys2-packages.ps1) requires that EXE filename, hash, and Authenticode signer (lines 64-66, 139-143, 200); it therefore cannot honestly qualify a TAR root even if the installed files match. [Preflight](../../../installer/preflight.ps1) probes only `C:\msys64` (line 75), whereas the guest used `C:\AutoClipMsysTar20261001\msys64`. The downloader can fetch a direct parent row and gated package children, but has no TAR signature-child route. The [manifest verifier](../../../scripts/verify-installer-manifest.py) checks generic direct prerequisites, but has no TAR-specific semantic checks. These are producer/consumer mismatches, not grounds to silently edit the selected v40 recipe or relabel the EXE as a TAR.

## Smallest intentional contract revision

Retain one `MSYS2` prerequisite identity, version `20260611`, x64 applicability, the five exact packages and signature records, and the native installed-file pins. Change its **base artifact** to the exact official TAR URL, filename, byte count and SHA above, with `artifact_kind: archive` (or one equally explicit TAR discriminator) and archive-specific provisioning steps. Replace QIFW `installer_arguments` with an explicit extractor/init/post-check contract; do not send `in --confirm-command ...` to `tar.exe` or claim the TAR has an Authenticode signer. Keep the GUI audit as historical evidence, not an alternate implicit runtime path. If both GUI and TAR are offered, they need separate explicit artifact records and selectors, which is more scope than the minimum route.

The manifest must be the single resolved input for both packaging validation and the wizard. Its TAR record needs: release-tagged official HTTPS source and exact redirect hosts; exact size/SHA; private-root layout (`msys64` under a new protected parent); extractor capability check; expected archive member policy/inventory; allowed locally generated post-install effects; initialization/exit checks; detection rooted at the **selected private path**; no expected reboot; and version-specific terms/licensing evidence. The detached `.sig` is its own child artifact with exact URL, 566 bytes, SHA-256 `076f5623b702d5016cf0253e1d14a6bd4870a90243243e96409b227f0d5bf70f`, redirect hosts and parent-gated classification. If the `.sha256` and `.packages.txt` are used by setup, each also needs its own exact artifact pin from IM-MS-02; neither may silently stand in for the authoritative manifest hash or an installed-package query. Record the installer key's full fingerprint, exact public-key acquisition provenance, and required signature-verification phase. A fetched public key is another separately controlled input; a fingerprint is the trust anchor, not a claim that a keyserver response is intrinsically trusted.

The [installer contract](../contract-v1.md) already requires exact download identity, a protected staging path, safe extraction, explicit vendor terms decision, cancellation and rollback, independent capability checks, and owned-file cleanup. Amend that contract only where the current “vendor installer” wording would otherwise require an executable installer or Authenticode check for this archive. Preserve `BLOCKED` on the MSYS2 parent and all five package/signature descendants until the complete direct-recipient route is implemented and qualified; descendants cannot authorize themselves. Do not alter the original v40 ZIP identity, recipe, package receipt, or source-build cache key to make this route appear successful.

### Windows native extraction and signature boundary

[Microsoft documents Windows `tar`](https://learn.microsoft.com/en-us/windows/tar/) as an included libarchive-based list/extract tool. That page does not establish `.xz` support on **every** Windows 10 build covered by the present setup contract. The current [platform preflight](../../../installer/preflight.ps1) admits Windows 10 x64 starting at build 10240; `tar.exe` availability and `.tar.xz` capability must therefore be measured on the actual recipient before downloading/committing to the TAR route. Select the absolute Microsoft `System32\tar.exe` (with appropriate 32-bit process redirection handling), validate its native signature/identity and successful `-tf` of the exact staged archive, then use a fixed `-xf ... -C <empty-owned-parent>` invocation and check its exit status. PATH lookup, PowerShell `Expand-Archive`, and a tool discovered inside an untrusted MSYS root are not equivalent preflight. If an in-scope Windows build lacks a capable native tar, either introduce an independently reviewed, pinned extractor dependency or intentionally revise the supported platform contract; no implicit fallback.

Windows `tar` is an extractor, not an OpenPGP verifier. The guest's `gpgv` result establishes the experiment, but the clean-recipient verifier bootstrap is **not yet specified**. A separately trusted verifier could check the pinned `.sig` against a fingerprint-checked key before extraction. Alternatively, exact manifest SHA may authorize safe extraction and then the hash-authenticated TAR's pinned `gpgv.exe` could verify the detached signature **before running bash/pacman**; that ordering needs an explicit contract decision because the verifier itself is archive-delivered and the current contract rejects an invalid *required* signature before executing a fetched artifact. Neither route is implemented or approved here. Do not substitute Authenticode for OpenPGP or treat the archive's package keyring as the installer signing key. Failure to provide a qualified verification order leaves the TAR route blocked even though the developer audit passed.

## Implementation and lifecycle boundaries to qualify

1. **Preflight, consent, acquisition.** Show the exact TAR publisher/source, size, purpose, root/elevation and terms decision before downloads or machine changes. Reject any existing/ambiguous root, path escape, reparse point, unsupported filesystem, insufficient space, or unqualified tar/signature verifier. Download TAR and each required child artifact through the normal redirect/size/hash/cancellation policy to protected staging; rehash just before use. Do not bundle the vendor TAR, key, packages, or signatures into setup without a separate approved route.
2. **Owned extraction.** Use a fresh, short ASCII NTFS parent with a protected ACL, no `subst`/network path, and a single expected `msys64` top directory. Inspect every member type/name for traversal, absolute paths, Windows-invalid names, case collisions and links; the exact audited TAR contains 15,529 files, 1,052 directories and no archived links ([IM-MS-04](IM-MS-04.md)). Do not merge with an existing MSYS2. After native extraction, compare the complete on-disk inventory and bytes to the authenticated archive, allowing only explicitly identified initialization outputs. Preserve a durable ownership receipt and distinguish complete from partial state; cancellation/error stops children and cannot delete shared/user directories or a pre-existing root. Retry only an exact matching, reverified stage.
3. **Native initialization.** Before first login, use the extracted, hash-checked native bash and `pacman-key` in a controlled non-login process for local **default** keyring `--init` and `--populate msys2`; verify full expected trust state. Then run one native login so the other upstream post-install scripts execute while the default keyring's refresh branch is skipped. Check each script's effects, expected `/etc/mtab` link target, home location, Windows file copies and absence of unexpected network/profile behavior. IM-MS-04 documents the exact five scripts and why an isolated package keyring alone cannot replace first login. The guest used a disconnected NIC; an ordinary online-recipient run still needs evidence that this exact ordering avoids keyserver traffic. Do not call `pacman-key --refresh-keys` or a repository update.
4. **Five packages and source build.** Revise the package helper to accept an exact **base archive path**, verify TAR identity/signature result and protected installed-root provenance, and remove GUI EXE/Authenticode assumptions. Keep its separate isolated trusted keyring, five exact packages plus signatures, repository-free `pacman -U`, unchanged unrelated base package snapshot, version/capability checks and fail-closed behavior. Resolve the child PowerShell launch policy through a documented first-party invocation, then obtain a fresh guest GREEN result; IM-MS-06 only fixed a socket-length bound. Make preflight and later detection use the selected private root, and pass its real `usr\bin\bash.exe` through the existing guarded `install.ps1 -MsysBash` parameter.
5. **Login startup and cache.** Follow [IM-MS-05](IM-MS-05.md): the immutable v40 recipe still makes four `bash -lc` receipt queries. Before guarded build, verify allowlisted `/etc/profile`, post-install/profile scripts and private HOME startup files; clear `BASH_ENV`/`ENV`; constrain HOME, GNUPGHOME, MSYSTEM, MSYS2_PATH_TYPE and PATH; protect the root against untrusted changes through build. Use a fresh isolated `-NativeBuildRoot` so an existing cache cannot skip the `-lc` path. Confirm receipt versions against independent non-login queries and preserve exact v40 cache/receipt semantics. A wrapper adapter is a larger change with new cache provenance and is unnecessary unless this real-bash route fails.

## Qualification and remaining decisions

The smallest meaningful RED/GREEN set is: manifest validation rejects a GUI/TAR mismatch, missing signature child, unapproved redirects and incomplete TAR metadata; downloader refuses a child while parent is blocked; archive fixture rejects traversal/link/collision/reparse paths and unsupported native tar; install fixture handles cancellation/partial root without touching unrelated files; package helper rejects GUI assumptions and then passes the exact TAR-root trusted transaction; preflight rejects wrong root or wrong installed-file/package versions; clean online guest observes no unintended keyserver traffic; and the guarded v40 source build reaches its real four `-lc` receipt calls with controlled profiles. Then run the contract's actual clean interactive wizard, health/media and lifecycle gates. No such RED/GREEN or end-to-end qualification was performed by this report.

Open decisions: the recipient OpenPGP verifier/bootstrap order; the minimum Windows 10 build on which native `tar.exe` supports this exact `.tar.xz`; how the wizard records and removes only its owned private MSYS2 root after cancellation/uninstall while retaining unknown files; and the separate vendor rights/terms decision. Until those are resolved and tested, **MSYS2 and its children remain `BLOCKED`** in the canonical manifest.

## Follow-up: use the already required Python, then verify the TAR signature

This bounded follow-up supersedes the **native Windows tar prerequisite** proposed above. The [Python 3.11 `tarfile` documentation](https://docs.python.org/3.11/library/tarfile.html) explicitly supports `r:xz` when `lzma` is available and exposes regular-file members through `extractfile()`. The current [Python prerequisite helper](../../../installer/install-python.ps1) already checks exact PSF-signed Python **3.11.9 x64**, headers/libraries, and an `lzma` compression/decompression round trip (lines 47-66). Read-only local probe of that exact installed Python with `-I -B` opened the pinned TAR and counted **16,581 members: 15,529 regular files, 1,052 directories**; its `tarfile.is_tarfile()` returned true. This proves local parsing capability, not a production extraction. It removes the Windows-build-specific native `tar.exe` question **if** the wizard installs or detects and verifies that same Python before starting MSYS2. Python itself remains a separately consented, exact pinned prerequisite, currently `BLOCKED` in the canonical manifest. The present Inno flow calls `PreparePython` before downloads in `PrepareToInstall` ([AutoClip.iss](../../../installer/AutoClip.iss), lines 491-508); actual MSYS2 integration must retain this dependency order and handle missing Python at its preflight/consent boundary.

The smallest safe Python extractor would inspect **all** members first, require this exact single `msys64` root and only directories/regular files, reject duplicate or case-colliding names, traversal, alternate path forms, reserved Windows names, links/devices and unexpectedly large members/counts, then create a fresh protected target. Use `extractfile(member)` **only after `member.isfile()`**, copy bounded bytes to exclusively created regular files under checked parents, verify the count and per-member byte lengths/hashes, and compare the final on-disk inventory. The Python docs warn that archives can contain duplicate names and unsafe extraction paths; do not rely on `extractall()` defaults or on a filter introduced/backported at a different 3.11 patch level. Do not apply arbitrary TAR owner/group, link, or device operations. Preserve/qualify required file modes and timestamps: the inspected `bash.exe` and extensionless `pacman-key` members both record mode `0755`, and a plain byte copy may not reproduce native `tar`'s MSYS-visible execution attributes. A fresh guest must run the default-keyring, login, package and source-build checks on **Python-extracted** bytes before declaring this route equivalent to the native-tar experiment. Recheck protected-parent ACL/reparse state throughout; exclusive creation alone does not settle Windows path races if an untrusted writer can change the parent.

No separately bundled per-file inventory is needed for the **exact** archive if the setup's authenticated dependency manifest pins its 53,555,380 bytes and SHA-256, the recipient download is rehashed, and extraction derives member names/sizes/hashes from that same authenticated archive in protected staging. Retain the inspected archive identity during extraction (or rehash the source afterward) and compare written files back to the derived inventory. The archive digest authenticates which member contents are expected; the extraction inventory checks that those contents landed at the intended paths. Fixed audit expectations (16,581 members, member type counts and top directory) are useful fail-closed semantic checks but are not a second independent cryptographic root. This design needs no additional 2.5 MB inventory payload or new extractor artifact.

The signature bootstrap can be made explicit without circular trust: (1) authenticate the manifest from the setup's existing fixed manifest hash; (2) verify the recipient TAR's exact size/SHA **before** treating any archive member as code; (3) use the verified Python to inspect and copy only regular files/directories into the protected root; (4) verify the copied `gpgv.exe` and its required DLL closure against bytes from that same hash-pinned TAR, launch that one verifier by absolute path with a constrained DLL/PATH search and an explicit keyring whose bytes/fingerprint are separately pinned to the official MSYS2 guide; (5) require valid detached `.sig` for the exact TAR and pinned primary signer before executing `bash.exe`, `pacman-key`, login, or package tools. This does execute a *hash-authenticated archive-delivered verifier* before its OpenPGP signature has been checked. That is a deliberate trust-order choice, not signature verification of an otherwise unauthenticated archive. The current [installer contract](../contract-v1.md) would need to state this narrow verifier-bootstrap exception to its “invalid required signature before executing” rule. A policy requiring OpenPGP verification before executing **any** archive-delivered binary would still require a separately trusted verifier and keep this route blocked. No recipient signature bootstrap, extraction, or production test was performed in this follow-up.
